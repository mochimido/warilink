# Security / Privacy / Regulatory Guardrails

この文書は技術・設計上の要件であり、日本の金融法務に関する最終的な法的意見ではない。実際の銀行データ取得・外部データ提供前に契約条件と専門家レビューが必要。

## 1. 最も重要な表示ルール

- **銀行入金照合済み:** 正式に取得した受取口座の入金明細と精算参照コード・金額等を機械照合した、という意味だけ。
- **本人が支払った証明ではない:** 振込依頼人名は変更可能な場合があり、コードを知る第三者が支払う場合もある。コードは認証要素でも秘密でもない。
- **支払債務の法的履行保証ではない:** 送金取消、組戻し、取引変更、誤入金、紛争がある。
- **未検出は未払いの証拠ではない:** 銀行データ反映遅延/接続断/摘要欠落/ことら等の異なる仕様。
- **送金申告済み:** アプリユーザーの申告だけ。銀行明細を確認したと誤表示しない。
- **受取人確認済み:** 受取人が手動確認しただけ。銀行APIによる証明とは別。
- 仮の銀行名・口座・コード・支払状態はDEMO表示する。productionで疑似マッチを許可しない。

## 2. セキュリティ

### 認証・権限
- ゲストセッションはランダムで長いトークン。hashをDB保存、httpOnly+Secure+適切なSameSite cookie、CSRF対策。
- 口座の追加/変更、銀行連携、データ同意・削除等には登録ユーザーのstep-up認証 (passkey)。
- グループ参加用URLは権限付与を最小限にし、第三者に転送・ログ経由漏洩されうると想定。公開グループページに口座詳細なし。
- 任意の group_member_id をリクエストbodyで指定されても、actorの操作権限をサーバー側で検証。
- API rate-limit、request size limit、画像画素数・MIMEの検査、signed uploadの短命化、OCRワーカーの資源制限。

### 口座保存・開示
- 銀行コード、支店コード、種別、口座番号、口座名義の入力バリデーション。
- payment destinationの原文をenvelope encryption（鍵version、rotation手順、復号監査）。ログ、分析、エラートレースに保存禁止。
- 他人に見せる際は**該当精算の支払者**に対してのみ、受取人が事前許可した場合に限る。フル番号の表示は積極操作＋限定有効期間。個人情報のコピーも監査対象。
- 受取口座変更時は旧versionを凍結し、支払者が古い情報を閲覧済みなら警告・再確認。
- サーバーが勝手に支払うAPI、振込予約API、銀行ログイン情報を預かる方式を実装しない。

### 銀行の明細取得
- `BankDataProvider`インターフェースを使用。正式な接続先・利用者同意・銀行とAPI事業者の契約・必要な登録/役割分担が確定するまでFEATURE_OFF。
- providerのread-only認可、最小の読み取りスコープ、暗号化されたtoken保管、revoke、expiry、更新エラー対応。
- 本人の銀行明細には給与・医療・家賃などが含まれうる。全履歴をサービスに送らず、用途・日付・入金のみの最小限を取得/保持。**取得範囲がAPI上絞れない場合もDBへの保存を最小化**。
- bank transaction matchesは他メンバーに金額と状態のみ共有。受取人の無関係な入金先/振込人/摘要をメンバーに表示しない。
- providerから取得したraw dataを外部広告・個人分析・販売・OCR学習に使わない。
- 金融庁の電子決済等代行業などの該当性、情報取扱いの契約条件は法務・連携先の審査後に最終決定。

### 照合アルゴリズムの脅威
- 金額のみ一致、コードの部分一致、曖昧な依頼人名一致では`matched`にならない。
- 参照コード7〜10文字は送金者本人の秘密ではない。推測耐性と衝突防止は必要だが認証目的では用いない。
- 取引データが再同期時に変更される場合あり、証跡の鮮度・重複防止・取消可能性を管理。
- 1取引の二重マッチ防止。振込手数料差引、複数件合算、部分入金、他人による代理送金は人手確認対象。
- 異議申立て・監査・確認取消を備える。不可逆に「支払完了」を確定しない。

### 2.1 本番設定の fail-closed(2026-10-20 実装、P03)

`WARILINK_ENVIRONMENT=production` のとき、API は次のいずれかに当たると**起動しない**(`app/core/config.py` の
`ensure_safe` / `production_problems`。`get_settings()` の初回呼び出し=アプリ生成時に検査)。

| 拒否する設定 | 理由 |
|---|---|
| `WARILINK_COOKIE_SECURE=false` | セッション Cookie が平文 HTTP で送られる |
| `WARILINK_ALLOWED_ORIGINS` が空・`*`・http・localhost/127.0.0.1・パス付き | CORS/Origin 検査が無効または開発用のまま |
| `WARILINK_DATABASE_URL` が開発用の既定パスワード(`warilink` / `warilink-dev-only`) | 既定の認証情報 |
| `WARILINK_FEATURE_BANK_PROVIDER=true` | 契約・同意・法務確認前 |
| `WARILINK_FEATURE_ADS=true` / `WARILINK_FEATURE_BILLING=true` | 未実装 |
| `WARILINK_ENVIRONMENT` が development/test/production 以外 | 綴り違いで開発設定のまま動くのを防ぐ |

- エラーメッセージは設定名だけを示し、値(DB のパスワード等)は出さない。pydantic の検証エラーも入力値を表示しない設定にした。
- 本番では状態変更リクエスト(POST/PUT/PATCH/DELETE)に `X-WariLink-CSRF: 1` と、許可リストにある `Origin` の**両方**を要求する
  (Origin なしも拒否)。開発・テストでは Origin なしを許す(既存のテストクライアント・ツールとの互換)。
- 本番では `/api/v1/docs`・`/api/v1/openapi.json`・`/redoc` を公開しない。
- Cookie 名(`wl_session`)・HttpOnly・SameSite=Lax は変更していない。Web は Next.js の rewrite で API を同一オリジンに見せるため、
  `WARILINK_ALLOWED_ORIGINS` には Web の https オリジンを 1 つ指定する。

### 2.2 レシート画像の保存期間とバックアップ(2026-10-20、P05)

- 保存期間を過ぎた画像は `scripts/warilink_purge_job.sh` で削除する(導入先で 1 日 1 回のスケジュールを設定。自動登録はしない)。
  画像と一緒に OCR の生の文字(`ocr_runs.tokens`・下書きの `lines`)も消す。削除できなかった画像は DB に記録せず次回再試行し、
  終了コード 1 と `WARILINK_ALERT_CMD` で知らせる。DB とファイルの不一致は `check-storage`(終了コード 2)で検出する。
- バックアップは `scripts/warilink_backup.py`。DB ダンプと画像を同時に取り、manifest に件数・スキーマ版・ハッシュだけを書く
  (接続文字列・パスワードは書かない)。出力ディレクトリは権限 700。
- 復元は `warilink_restore_*` の新しい DB と空ディレクトリにだけ行い、ハッシュ・行数・スキーマ版・外部キー・アプリからの読み戻しを確かめる。
  既存・共有 DB への復元は拒否する。
- **未実施**: バックアップの暗号化、外部保管、保管期間、本番への切り戻し手順(保管先・鍵が決まってから)。
  バックアップにはレシート画像(個人情報)が含まれるため、削除の期限はバックアップの保管期間にも及ぶことに注意(未設計)。

### 2.3 Passkey(P07、2026-10-20)

- 任意。登録しなくても割り勘・精算・OCR はすべて使える(振込先の保存だけは登録済みのみ。P08)。
- challenge は使い捨て・既定 300 秒。登録は開始した identity とセッションに、ログインは開始したセッションに結びつける。
  RP ID(未指定なら `allowed_origins` の最初のホスト名)と Origin(`allowed_origins`)を検証し、ユーザー検証(UV)を必須にする。
  署名回数が戻った応答(認証器の複製の疑い)は拒否する。本番では RP ID が Web のホスト名と合わなければ起動しない。
- 登録・ログインのたびにセッションを作り直し、古いトークンを失効させる(セッション固定の防止)。
- 復元: Passkey をすべて失った場合は復元できない。メール・SMS などの弱い本人確認でアカウント・振込先の権限を渡さない。
  紛失した端末のログインは「ほかの端末のログインをすべて解除」で失効できる。
- 未実装: アカウント削除(退会)。設計上は「Passkey とセッションを失効 → identity を無効化 → 振込先を削除 → 参加中のグループの
  メンバー行は名前だけ残す(支出・精算の整合を保つ)」とする。

### 2.4 振込先(P08、2026-10-20)

- 保存は Passkey 登録済みの本人だけ。登録・変更・自分の全桁表示は直近 10 分以内の Passkey 確認(step-up)が必要。
- 暗号化はエンベロープ方式(版ごとの DEK + 版つきの KEK、AES-256-GCM、AAD で行・所有者に結びつける)。KEK は環境変数で渡し、
  DB・バックアップ(`scripts/warilink_backup.py`)には含まれない。KEK を失うと復号できない(テストで確認)。
- 本番: KEK が未設定なら振込先の機能だけを止める(503)。開発用の固定鍵・不正な鍵の設定は起動を拒否する。
  **KMS 等の鍵管理サービスへの移行は未実施**(本番の環境が決まってから)。
- 表示できるのは、その送金の支払者だけ。オーナー・同じグループの他のメンバー・外部の人には存在も知らせない(404)。
  受取人が共有を取り消すと、以後は表示しない(既に見た人の記憶やメモは消せない)。
- 受取人が変更しても、支払者に最初に見せた版は書き換えず、変更を警告する。
- 監査ログ・エラー・URL には口座番号・名義・暗号文を出さない(テストで DB とログを検査)。
- アプリは送金・銀行ログインを行わない。照合コードは送金の目印で、支払いの証明ではない。

## 3. 個人情報と同意

- サービス提供（必須用途）と、OCR改善、パーソナライズ広告、統計・市場分析（それぞれ任意）は別に説明。
- `consent_records` にはpurpose、文書version、時刻、撤回、同意の取得経路を保存。
- OCR訂正を本人の確認なしにモデル学習へ投入しない。他人の負担者情報を含むレシートで、アップロード者だけの同意を全員分の同意と扱わない。
- 購買履歴販売・ユーザー別購入履歴の第三者共有はMVP外。統計情報の加工・小セル再識別リスク・匿名加工情報に該当する場合の義務を検証。
- 記録された「負担額」は実際の個人消費を必ず示すわけではない。広告や市場分析に推測を過度に利用しない。
- 原本に電話番号/カード末尾/会員IDなどが写っている可能性。取得目的に不要なら保存期間短縮・削除・表示時マスキング。
- 利用者に本人データの参照、共有解除、訂正、削除、同意撤回を提供（法令・契約での例外は透明化）。
- ゲストユーザーのCookieやブラウザ保存は本人同一性を完全保証できない。リカバリーはpasskey/適切な認証へ誘導。

## 4. OCR/広告・有料のセキュリティ

- 端末OCRはprivacyとコストに有利だが、ブラウザメモリ、認識精度、モデル再配布と動作保証が課題。
- サーバーOCRの無料枠は `ocr_quota_ledgers`で原子操作。ジョブの再試行・中断・同一画像の重複で誤請求しない。
- 広告報酬のクライアントイベントは改ざんされうる。1人・端末・ネットワークへのスロットリング、報酬の絶対上限、nonce再利用防止。導入広告SDKの条件によってはサーバー側の不正防止証明が得られないことを明記。
- 有料プランの「サーバーOCR無制限」は初期には不可。SLA/濫用対応を明記したfair useでも消費者誤認に注意。明示枚数のあるプランから検証。
