# Product Requirements Document (PRD) — WariLink

基準日: 2026-10-16 / 対象: 日本国内向けモバイル優先Webアプリ / 状態: 実装仕様草案

## 1. 北極星指標

「グループ作成→支出登録→負担確定→未払い解消」を、安全・正確・短時間で完遂できる比率（精算完了率）。
副次指標: OCRレシート完全一致率、平均訂正秒数、精算1件の画面操作数、招待参加率、bank-match候補誤判定率、OCR/アクティブユーザー原価。

## 2. ユーザー・権限

- `guest`: アカウント登録不要・メール不要。ゲストセッション+招待URLのグループ参加。手動割り勘、レシートOCR基本枠、金額・精算先確認、送金申告。
- `registered_member`: Passkeyなどでアカウント化したユーザー。永続プロフィール、銀行口座・PayPay ID登録・複数グループ再利用・自分の振込先の共有制御・通知管理。
- `group_owner`: グループ招待・参加者管理・イベント閉鎖。管理者でも他人の銀行接続認可は操作できない。
- `payer`: 精算額の支払義務者。支払申告可、振込先は必要最小限の権限で閲覧。
- `payee`: 精算額の受取人。受取申告確認、銀行連携同意、入金候補の確認・否認。
- `service_admin`: 利用規約、プラン、メトリクス、監視。実レシート・銀行履歴・振込先の無条件閲覧不可。

## 3. 主要フロー

### F1 ゲスト割り勘
1. LPで「登録せず始める」。ランダムな匿名セッションとCookieを生成。
2. グループ作成→名前・参加人数→期限付き招待URL発行。招待リンクとは別にメンバーの編集権限を管理。
3. 支出入力: 誰が立替/何円/誰が負担/均等・割合・比率・指定額。
4. 計算後にプレビューし、本人が支出・配分を確定。
5. ネット残高を更新し、送金先・金額を表示。

### F2 OCRレシート→商品ごとの割当
1. 写真を選択。画像サイズ・MIME・ピクセル上限・悪意あるファイルを検証。
2. OCR枠の原子的予約。画像はprivate storageへ署名付き短命アップロード。
3. 非同期ジョブに登録。workerで方向/ぼけ検出、PaddleOCR、BBox座標、明細解析。
4. `receipt_draft`にraw + structured + confidence + warnings。店舗名/日付/明細/数量/単価/行金額/値引/税/小計/請求総額。
5. 画像と各行を並べて確認。金額・数量・明細が訂正可能。`sum(lines)+adjustments = total`を検証。
6. 各商品で負担する人を選ぶ。合計をexact integer apportionmentで分配。
7. 支出確定→残高に反映。OCR修正は明示的同意があるときのみ学習候補になる。

### F3 登録済みユーザーの振込先
1. ゲストが任意にPasskeyを登録。セッション内データを同一人のアカウントへ安全に昇格。
2. 受取人が本人の口座情報（銀行コード/支店コード/口座種別/番号/名義）とPayPay IDを登録。
3. 振込先保存と振込先共有を分離。受取人が精算先共有を有効化。
4. 送金者が精算画面に来たとき、当該精算へのアクセス権を検証して振込先を限定開示。情報を静的公開URLに埋め込まない。
5. 口座変更時はrecipientの再認証を必要とし、過去の支払表示のバージョンと変更警告を残す。

### F4 銀行振込の識別コード
1. サーバーが`settlement_reference`ごとに暗号学的乱数の7〜10文字程度の英数字コードを発行。照合可能期間と用途・受取口座versionを紐付ける。
2. 「振込依頼人名」に`CODE 氏名`を追加する案内、コピー操作を提供。
3. 受取銀行の正式な明細取得が使える場合、受取口座・受取金額・コード・取引日時・二重照合なしを検証。
4. 成功しても表示は「銀行入金照合済み」。送金者本人の認証と法的支払保証はしない。
5. 一致条件を満たさない/情報が欠落する取引は`match_candidate`→本人確認。銀行により振込名義が省略・変更・省略される場合を扱う。

### F5 銀行連携がない場合
- 受取先表示→金額・コードをコピー→本人が銀行アプリで送金→「送金申告済み」→受取人が手動確認。
- PayPay/ことら/現金はコード検証を保証しない。送金者申告+受取確認。PayPayの自動送金・自動金額セットは初期スコープ外。

### F6 OCR無料/広告/有料
- Free: 匿名/登録ともOCR **月3枚**（サービス内の対象単位を厳格定義）。手入力は無料、商品別配分も無料。
- Rewarded Free: 対応広告が正常に配信され、報酬付与条件を満たした場合、追加で**最大7クレジット**、計10枚を目安。配信保証しない。1広告=1クレジットを仮置き。付与はサーバー上限・冪等管理。
- Pro: 有料プランは **月100〜300枚を検証**。高負荷利用を一律「無制限」と宣伝しない。ブラウザ内OCRは別機能として将来検証。
- 初期は課金mockのみ、決済プロバイダ契約後に本番決済。登録なしでもFree利用可能だがProの契約管理に永続認証手段が必要。
- 利用枠: タイムゾーンAsia/Tokyo、月初リセット、アップロード1原本の成功で1枠消費、内部エラーは返還。意図的な画像再送信や同一ファイルは重複判定。無料枠の絶対的な不正防止は不可。

### F7 OCRの継続的改善
- `ocr_model_version`, preprocessing version, raw tokens/BBox/confidence, parsed lines, warnings, user revisions を保存。
- 修正前後の原本を区別し、編集権限や変更時刻を保持。
- 明細パーサーのルールを先に改善、次にconfidence calibration、十分な許諾と検証が得られたらOCR fine-tuning。
- 適切な同意を得たデータだけをトレーニングセットに。少数サンプルから精度99%などを謳わない。学習データと評価データは店舗・レイアウト単位で分割。

### F8 データ二次利用と広告
- 通常のコンテキスト広告は広告仕様・外部送信に従って実施。
- `consent_ocr_learning`、`consent_personalized_ads`、`consent_market_analytics`は別opt-in、初期OFF、撤回機能とバージョン履歴。
- 一部参加者が未同意ならその参加者の個人別配分データを他人の同意で二次利用しない。
- 銀行明細は送金照合だけ。広告・原本販売・購買データ売却対象外。
- レシート原本と個人別割当の無条件第三者販売を初期版で禁止。統計データ販売は法務・再識別テスト・企業需要調査後。

## 4. 画面一覧

- `/` LP: キャッチコピー / 登録せず開始 / 機能説明 / SEOコンテンツ。
- `/g/[publicId]`: グループ概要、参加者、総支出、自分の残高、一覧。
- `/g/[publicId]/expenses/new`: 支出入力（現金・振込先には触れない）。
- `/g/[publicId]/receipts/new`: 撮影/アップロード・OCRジョブ進行。
- `/g/[publicId]/receipts/[id]/review`: 原本と認識項目の対照・修正。
- `/g/[publicId]/allocations/[id]`: 明細単位の負担者トグル/税・割引。
- `/g/[publicId]/settlements`: 送金提案・送金申告・受取確認。
- `/payments/[transferId]`: 金額・振込先の限定表示・照合コード・状態（アクセス制御必須）。
- `/account`: 任意登録・Passkey・プロフィール・口座マスキング・共有設定。
- `/account/bank-connections`: 契約後の銀行API連携（初期はデモ/無効）。
- `/account/privacy`: 目的別同意の確認/変更/撤回/削除要求。
- `/plans`: 3枚無料+追加報酬枠+有料の比較。

## 5. 非機能要件

- モバイルファースト、アクセシビリティ（WCAG 2.2 AAを目標）、タップターゲット44px目安、フォーカス、読み上げ可能な状態表示。
- すべての操作は途中から復帰できる。OCRジョブのprogressとretry。画像の品質不良で手入力へフォールバック。
- SEO対象はLPと公開ガイドだけ。グループ・支出・支払・銀行情報は`noindex`、非公開、キャッシュ禁止。
- p95 API遅延/ピーク時OCR待機/エラー率を監視。具体的SLOは負荷測定後確定。
- JPY金額の整数化、全ての変更にrevision/optimistic locking/冪等性。
- 削除・グループ解散・同意撤回は仕様と監査範囲を定義し、個人データを永久保存しない。

## 6. 明確な非対応

- PayPay/銀行への自動送金実行、自動金額入力の未公開deep link。
- 銀行ID/パスワードをサーバーに預かるスクレイピング。
- PayPay送金履歴を非公開APIから取得。
- 本人の法的身元保証や「支払いを100%保証する」機能。
- レシート・銀行履歴の無断広告利用・原本販売。
- 金融データprovider契約なしでの実口座データ取得。


## 7. 追加要件の反映(2026-10-18)

- 精算: 少人数(既定20人以下)は厳密な最小送金件数を求め「最小送金回数」と表示。超過時は「送金回数を削減」(最小保証なし)。最適化の前提(送金先制限なし・手数料なし・上限なし・JPYのみ)を画面/APIで明示。確定済み・照合済み送金は再最適化しない。詳細 `docs/SETTLEMENT_ENGINE.md`。
- 商品別割り勘UI(Phase 2): 負担者のワンタップ選択/解除、全員、前の商品と同じ、複数商品の一括割当、数量単位(例: ビール3杯をA2・B1)、不均等負担、税・割引・クーポン・サービス料の明示ルール、変更ごとのサーバープレビュー、未割当/金額不一致/OCR低信頼の視覚区別。
- レシート不一致: 自動補正しない。訂正または差額調整行の明示追加まで確定不可。
- OCR利用枠: 無料月3枚・広告追加・合計上限(約10枚)・Pro枠は**設定値**で管理(コード定数にしない)。
- OCR改善: 生結果と確定訂正の分離保存、文字認識誤りと対応付け誤りの区別、同意データのみ、訂正は検証前に正解ラベルとしない、モデル交換可能なアダプター、評価データセットと悪化防止ゲート(`DATA_MODEL.md §6`)。
